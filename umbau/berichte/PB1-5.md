**Kür** (freiwillig, zählt nicht zum Fortschritt):

- Beim Überschreiben bleiben Name und Parameterliste gleich und der Rückgabetyp passt zu dem der Oberklasse; die Sichtbarkeit darf gleich bleiben oder weiter werden (etwa protected → public), aber nie enger. Private Methoden der Oberklasse sieht die Unterklasse nicht und kann sie deshalb nicht überschreiben; über super kann die neue Fassung die alte mitbenutzen. _(buch:FS-3.3.2, buch:FS-3.5.3)_
- Ein Destruktor ist das Gegenstück zum Konstruktor: Er läuft als Letztes, bevor ein Objekt entfernt wird, etwa um eine Datei zu schließen oder Daten zu sichern. In Sprachen mit Garbage Collector (z. B. Java, C#, Python) wird der Speicher nicht mehr erreichbarer Objekte automatisch freigegeben, deshalb braucht man Destruktoren dort kaum und schließt Ressourcen besser ausdrücklich, etwa im finally-Block. _(buch:FS-3.5.3, buch:FS-3.6.1)_
- SOLID fasst fünf Entwurfsprinzipien zusammen: Single Responsibility (jede Klasse eine Aufgabe), Open-Closed (offen für Erweiterung, geschlossen für Änderung – Neues kommt über neue Unterklassen oder Implementierungen), Liskov Substitution (ein Objekt der Unterklasse muss überall statt eines Objekts der Oberklasse funktionieren und darf deren Verhalten nicht einschränken), Interface Segregation (lieber mehrere kleine Interfaces als ein großes) und Dependency Inversion (Fachlogik und Technik hängen beide von Abstraktionen wie Interfaces ab statt direkt voneinander). Alle fünf zielen auf lose gekoppelte Klassen, die sich ohne Eingriff in getesteten Code erweitern lassen. _(buch:FS2-2.1.4)_
- Standardbibliotheken liefern fertige Datenstrukturen als Collections: Interfaces wie List, Set oder Map legen fest, welche Operationen es gibt, und mehrere Klassen setzen sie unterschiedlich um, etwa eine Map als Hashtabelle oder als sortierter Baum. Wer im eigenen Code nur das Interface als Typ verwendet, kann die Umsetzung später austauschen. _(buch:FS2-2.2.4)_

**Kür** (freiwillig, zählt nicht zum Fortschritt):

- Der Softwareentwurf baut auf den Anforderungen auf und ist unabhängig von der Programmiersprache: Erst legt der Architekturentwurf den Grobaufbau aus Subsystemen, Modulen bzw. Klassen und ihren Schnittstellen fest, dann der Detailentwurf je Modul Datenstrukturen, Datenmodell und Algorithmen (im Wasserfallmodell einmal, agil in jeder Iteration). Ergebnisse sind Modelle wie Klassendiagramm und ER-Modell, die Wahl des Datenbanksystems, die Schnittstellen zu vorhandenen Systemen und schon die Planung der Tests. _(buch:FS2-1.2.1, buch:GS-5.5.3, buch:GS-5.4.1)_
- Die Softwarearchitektur ist der Bauplan aus Komponenten und ihren Verbindungen; sie wird vor allem von Qualitätsanforderungen wie Wartbarkeit, Sicherheit und Performance bestimmt und lässt sich später nur mit großem Aufwand ändern. Merkmale einer guten Architektur sind neben Modularität und geringer Kopplung auch Einfachheit (je Aufgabe ein Modul), Vollständigkeit gegenüber den Anforderungen und die Möglichkeit, Teile parallel auszuführen. _(buch:FS2-1.2.1)_
- Modularisierung wirkt auf mehreren Ebenen: Methode oder Funktion (genau eine Aufgabe), Klasse (das typische Modul der Objektorientierung) und Softwarekomponente (bündelt mehrere Klassen zu einem fachlichen Dienst). Eine Schnittstelle bietet nur so viel nach außen an wie nötig, weil das die Kopplung gering hält und weniger Testfälle erfordert. _(buch:FS2-2.1.1)_
- Clean Code heißt, Code so zu schreiben, dass andere ihn schnell verstehen und ändern können – mit Team-Konventionen, sprechenden Namen, benannten Konstanten statt „magischer Zahlen“, kleinen Funktionen mit wenigen Parametern und nur nötigen Kommentaren –, weil der größte Teil der Arbeit Änderungen an bestehendem Code sind. Refactoring verbessert die innere Struktur von Code (Namen, Aufteilung, doppelten Code), ohne sein Verhalten zu ändern; Tests sichern dabei ab, dass alles weiter funktioniert. _(buch:FS2-2.1.4)_
- Bekannte Faustregeln sind KISS (so einfach wie möglich), DRY (jede Information und Logik nur an einer Stelle, mehrfach gebrauchter Code in eine Funktion) und YAGNI (nur bauen, was jetzt verlangt ist, auch keine Optimierung auf Vorrat). Das Gesetz von Demeter (nur mit direkt bekannten Objekten zusammenarbeiten) und „Tell, don’t ask“ (einem Objekt sagen, was es tun soll, statt seine Daten abzufragen und außerhalb zu verarbeiten) halten die Kopplung gering. _(buch:FS2-2.1.4)_

- Das Adapter-Muster (Strukturmuster) macht eine vorhandene, nicht änderbare Klasse – etwa aus einer fremden Bibliothek – unter der Schnittstelle nutzbar, die das eigene Programm erwartet: Die Adapterklasse implementiert diese Schnittstelle und leitet die Aufrufe weiter, entweder an ein gehaltenes Objekt (Objektadapter) oder über Vererbung (Klassenadapter). _(buch:FS2-2.1.3)_
